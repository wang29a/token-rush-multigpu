# 多卡优化实验手册

> **这是学习用的阶梯，不是项目计划。** 项目计划（值不值得做、1.5x 的账怎么算、
> 报告怎么写）在 `docs/multigpu.md`。这本手册只回答一个问题：**怎么一级一级
> 把它学会，并且每一级都能说清楚瓶颈在哪、下一步为什么是它。**

## 0. 一句话方法

单卡那套循环你已经跑熟了：**问一个问题 → 先写预测 → 做最小改动 → 测一个数
→ 解释预测和实测的差 → 决定下一步**。多卡完全沿用这个循环，但要换两样东西：
**尺子**和**瓶颈清单**。循环不改，改的是怎么看数。

## 1. 循环不变，换两样东西

### 1.1 尺子：从一把变成四把

单卡只看一个数：% of wall。多卡要同时看四个，因为它们会互相打架：

| 指标 | 定义 | 它回答什么 |
|---|---|---|
| **S(n)** | T(1) / T(n) | 加卡到底快了多少 |
| **E(n)** | S(n) / n | 加卡的效率；2 卡 1.5x → E = 0.75 |
| **comm share** | 通信时间 / 步时间 | 这次切分是不是被通信吃掉了 |
| **straggler** | max(rank 时间) / mean | 是不是有一张卡在拖后腿 |

再加一个不随实现漂移的：**% of aggregate wall**（n × 1701 GB/s 做分母）。它
和单卡那个 81% 是同一把尺子，只是分母变了——2 卡上它会掉到 60% 出头，这不是
退步，是 TP 的价格，你要能提前算出来。

### 1.2 瓶颈清单：单卡六查 + 多卡三查

单卡你已经会查：带宽、延迟、启动、占用、host、缓存。多卡加三条，而且这三条
是新的：

1. **重叠检查**：step 时间 ≈ compute + comm（串行），还是 ≈ max(compute, comm)
   （重叠）？前者说明关键路径上一次通信都没藏住。用 nsys 看两条 rank 的
   timeline 之间的空隙，不要靠猜。
2. **通信占比检查**：comm / step。> 20% 说明下一步该动通信；< 5% 说明通信不是
   问题，别在上面浪费时间。
3. **木桶检查**：max(rank) / mean(rank)。> 5% 说明分片不均（rank 0 多做了
   采样、KV 长度不对称、某个 shard 边界切在了不对的地方）。

## 2. 试验台：两个台子，一只老鼠

### 2.1 卡：主台用 5090，对照台用 NVLink

阶梯里真正在变的只有四个量：**每卡带宽、链路延迟 L、链路带宽、batch**。只在
一个硬件点上跑，你只会得到一个点，而且容易把"5090 上的 1.5x"当成 TP 的普遍
规律。所以需要两个台子，但常驻的只有一个。

| 台 | 配置 | 价格 | 它教什么 | 它不能教什么 |
|---|---|---|---|---|
| **主台** | 2 × RTX 5090（PCIe，无 NVLink，P2P 默认关） | ~$1.2–4/hr | 最差互联下的 TP：通信代价被放大，机制看得最清；和项目同构 | 看不到"好互联"下结论怎么翻 |
| **对照台** | 2 × A100 80G SXM（NVLink 600 GB/s），3–4 小时 | ~$1–1.5/卡·时 | 同一套代码、L 小 3–5 倍、带宽高 1.2 倍；看 break-even 怎么翻 | 贵；只能跑短实验 |
| 可选 | 4 × 任意卡，跑 S7 的 n=4 列 | — | 扩展性曲线 | — |
| 可选 | 8 × H20（国内常见：NVLink 900 GB/s、96 GB、4 TB/s、算力弱） | 便宜 | 把"带宽 vs 算力"单独拉出来：decode 飞快、prefill 很慢 | 算力弱，prefill/EP 结论会失真 |

**最小可行**：2 × 5090 常驻 + 2 × A100 SXM 三小时。**够用**。
**租之前先花 $3 测供应商的板子**：同一个"2×5090"实例可能是 x16/x16，也可能是
x8/x8，也可能两张卡挂在不同 PCIe switch 上——`nvidia-smi topo -m` 和 S1 的
延迟数决定这台机器值不值得按小时租下去。这一步本身就是 S1。

### 2.2 老鼠：Qwen3-8B（bf16 + 一个 int4 版本）

单卡 16 GB 能跑（TP=1 的基线在同一台机器上）、2 卡跑 TP=2、4 卡跑 TP=4/PP=4；
hidden 4096、三十几层，离真身（5120 / 64 层）不算太远；HF 实现干净；有现成 int4。

换成别的模型时逐条看这个清单：

- `num_key_value_heads` —— **决定 TP 的上限**。8 个 KV head 的模型能到 TP=8；
  真身只有 4 个，所以 TP≤4。这个差别本身就是 S7 上要量的一课。
- `hidden_size` —— 每次 all-reduce 的 payload = hidden × 2 B。真身是 10 KB。
- `num_hidden_layers` —— 每 token 的集合通信次数 = 2 × 层数。
- 有没有 GDN / 线性注意力 —— **老鼠最好没有**，先把纯 Transformer 的 TP 学
  明白；真身有，那要多一类分片（按 head 切 + depthwise conv），S10 再面对。
- 有没有现成 int4（GPTQ / AWQ / GGUF）—— S3 要用它量"量化越狠、TP 越不划算"。

**老鼠引擎不要写任何 arch-specific kernel。** 用 PyTorch + Triton 写，同一个
文件在 5090 和 A100/H100 上都能跑——否则对照台那三小时就白租了。

**真身**：Qwen3.8-27B int4 4.25 bpw，只在 S10 上。

**老鼠的结论不能引用。** 它 hidden 更小、层数更少，通信占比会被放大——对学习
是好事（看得清），对报告是坏事（数字不迁移）。这条要写在日志第一行。

## 3. 十一级台阶（外加一个可选分支 S7+）

每一级都是"基线 → 一个优化 → 一个数 → 一个决定"。过关线没过就不要往上爬，
先回答为什么。

| 级 | 基线 | 这一步的优化 | 测什么 | 过关线 |
|---|---|---|---|---|
| S1 | 单次 `memcpyPeer` | 图内 + P2P 开关 | L(10 KB)、带宽、拐点 | L(10 KB) ≤ 15 µs |
| S2 | NCCL all-reduce | 自写 one-shot（写 + flag + spin） | 10 KB / 1 MB / 64 MB 的 µs | one-shot 在 10 KB 快 2x |
| S3 | 单卡一层线性 | 切 N / 切 K + all-reduce | M 扫描下的四种切法 | 能提前预测翻转点 |
| S4 | eager 64 层链 | 两张图 / NCCL 进图 / spin 进图 | 启动税 ms/step | 图比 eager 快 ≥3x |
| S5 | 1 层 block | 64 层 + AR 融进 residual+norm | comm share、straggler | 64 层时 share ≤ 25% |
| S6 | 单卡老鼠 | TP=2 整机 | S(2)、% 聚合墙、正确性 | ≥ 1.4x |
| S7 | TP | PP / DP / PP+TP | bs ∈ {1, 8, 64} 的地图 | 每一格能一句话解释 |
| S7+ | TP=2（稠密） | EP / all-to-all（MoE，可选） | bs=1 vs bs=32 的字节账本 | 能说清 bs=1 为什么 EP 不划算 |
| S8 | 串行 AR | 双 micro-batch / 分块 AR | 重叠率（对比 sum 与 max） | 藏掉 ≥ 30% 通信 |
| S9 | TP prefill | ring / 序列并行 | 32k / 128k prefill | SP 比 TP 快 ≥ 20% |
| S10 | 老鼠的模型 | 27B 真身 | raw / spec / 200k | 与投影差 ≤ 10% |
| S11 | 一堆表 | 决策备忘 | tok/s/$、tok/s/W | 能讲清取舍 |

### S1 — 链路（0.5 天）

- **问题**：这张卡到那张卡，一条消息多少钱？多大以后带宽才接管？
- **建**：`lab/01_link.py`。`nvidia-smi topo -m`、`torch.cuda.can_device_access_peer`；
  64 B–256 MB 双向 ping-pong；eager 和图内各一遍；再用 NCCL broadcast 做对照。
- **先写预测**：L(10 KB) ≈ 5–10 µs，带宽 ≈ 25–50 GB/s，拐点 ≈ 256 KB。
- **大概率会看到**：x8/x8 的板子带宽直接腰斩；P2P 关着时 L 翻倍。
- **教什么**：延迟和带宽是两个 regime。10 KB 永远在延迟那一侧——这是整条阶梯
  的第一块基石。

### S2 — 集合通信（1 天）

- **问题**：TP 要用的那个集合通信，在我们这个消息大小上到底多少钱？
- **建**：all-reduce / all-gather / reduce-scatter / broadcast，10 KB / 1 MB /
  64 MB，2 卡与 4 卡；NCCL 对照自己写的 one-shot（每张卡把分片写到所有对端 +
  置 flag + spin + 归约）。
- **先写预测**：10 KB 时 one-shot 比 NCCL 快 2–3x；64 MB 时 NCCL 反超。
- **教什么**：ring / tree / one-shot 各自的适用区间；为什么 vLLM、SGLang 都
  自己带 all-reduce kernel，而不是直接用 NCCL。

### S3 — 一层线性，四种切法（1 天）

- **问题**：什么时候把一层切两半，比不切更快？
- **建**：一层 `[N, K]`，M ∈ {1, 8, 64, 512, 4096}；四种做法：单卡 / 切 N（输出
  维）+ all-reduce / 切 K（输入维）+ all-reduce / 单卡 split-K（对照）。
- **先推公式**：T₂ = T₁/2 + comm，所以 **comm < T₁/2 才赢**。M=1 时 T₁ 是
  字节/带宽，这条式子就能直接算。
- **先写预测**：M=1 切 N 赢在字节减半；**int4 比 bf16 更容易输**——因为要切的
  字节少了，量化越狠，TP 越不划算。这是这个项目和量化工作的一个真实连接点。
- **教什么**：break-even 方程。为什么 `lm_head`（N 巨大）适合切，小投影不适合。

### S4 — 双卡图捕获（1 天）

- **问题**：整步还能不能是一张图？不能的话启动税是多少？
- **建**：64 层玩具链（GEMV + all-reduce + norm）；eager / 两张 per-device 图 /
  NCCL 进图 / one-shot spin 进图，四种各测一遍。
- **先写预测**：eager 比图慢 3–10x（每次 launch 5–10 µs × 两百次）。
- **教什么**：单卡上那个 9.11 ms 的启动税，在多卡上会原样回来。图是后面所有
  测量的前提——图不成立，后面的数全是 host 时间。

### S5 — 一层块，然后一叠（1 天）

- **问题**：通信占比随深度、宽度怎么变？
- **建**：老鼠形状的 TP block，跑 1 / 8 / 32 / 64 层；把 all-reduce 融进
  residual + RMSNorm（sum 里多一个分片而已）。
- **先写预测**：每层占比基本不变；固定成本随深度摊薄。
- **教什么**："深"对 TP 友好，"宽"不一定；固定税从哪里来、为什么它不随 n 变小。

### S6 — 老鼠整机（2 天）

- **问题**：所有东西接到一个真模型上，还成立吗？
- **建**：约 300 行 TP 引擎：权重分片（head 维、KV head 维、vocab 维）、KV
  分片、图、采样合并、decode 循环。正确性用 TP2 vs TP1 的 logits 比，首次分歧
  看 top-5 里有没有参考 token。
- **过关**：≥ 1.4x；不到就带着 S5 的数回去查固定成本。
- **教什么**：分片的边界在哪；采样合并必须**两卡各自重算且确定性**，否则一张
  卡接受 3 个 draft、另一张接受 4 个，两个状态静默错位。

### S7 — 并行菜单（2 天）

- **问题**：TP / PP / DP / PP+TP，谁在什么 batch 下赢？
- **建**：同一只老鼠跑四种策略；bs ∈ {1, 8, 64}。
- **产出**：**3×4 的地图**（行=策略，列=batch，格=tok/s 和 comm share）。这张
  表就是"多卡优化策略"的全部答案。
- **教什么**：PP 在 bs=1 输（把投机已经摊掉的权重又按行重读一遍），在 bs=64
  赢；DP 永远 2x 但延迟不变。每一格都要能用一句话 + 一个数解释。

### S7+ — MoE 那一行（可选，2 天）

先说结论：**你的项目不需要为 MoE 改设计**（27B 是 dense + GDN），但**学多卡要补
这一节**，因为 2026 年的主战场在 MoE，而且它会把 S7 的地图按 batch 劈成两半。

- **问题**：模型换成 MoE 之后，前面几级的结论哪些还成立？
- **建**：一个 30B 级、激活 3B 左右的 MoE（Qwen3-30B-A3B 这一档），int4 约
  17 GB，2 卡装得下。测三件事：(a) bs=1 每 token 实际读多少字节、tok/s；(b)
  bs=32 时 all-to-all 占步时间多少；(c) 同一模型 TP=2 与 EP=2 的对比。
- **先写预测**：bs=1 时 MoE 比同参数稠密模型快得多——只读激活的 3B，不读 30B；
  EP 在 bs=1 是负收益（一个 token 的 all-to-all 纯 latency）。batch 到 32 以后
  反过来，all-to-all 和专家负载不均变成主菜。
- **教什么**：MoE 换掉了前面"字节 → 墙"的整本账：稀疏激活让 bs=1 的带宽成本
  按激活比例打折，而 batch 一上来，成本从"读权重"变成"搬 token"。同一个模型、
  同一张卡，两个 regime 的最优并行方式完全不同——这正是 S7 那张地图要表达的
  东西，只是多了一维。

三个变化，按重要性排：**并行轴从 TP 变成 EP（all-to-all）**；**显存从"参数/卡"
变成"专家摆放"**（热点专家会拖垮最慢卡，straggler 检查在这里第一次真正生效）；
**bs=1 的账本整个反过来**（稀疏 = 少读，而不是"切得动"）。

### S8 — 重叠（1–2 天）

- **问题**：128 次 all-reduce 里，能藏起来多少？
- **建**：把 M=8 的 verify 行拆成两个 micro-batch，让第 0 个的 all-reduce 和
  第 1 个的计算重叠；再试分块 all-reduce。
- **先写预测**：M=1 时一点都藏不了（没有独立工作）；M=8 能藏 30–40%。
- **教什么**：**是投机解码给的 batch 让重叠成为可能**。这是单卡项目和这个
  实验之间的一个真实连接点，也是"为什么 bs=1 的 TP 这么难"的最直接证据。

### S9 — 长上下文 / 序列并行（1 天）

- **问题**：prefill 用序列并行比 TP 多拿多少？
- **建**：32k / 128k 的 prompt 切两半，ring attention（复用现成实现，别自己写）。
- **先写预测**：SP 1.7–1.9x，TP 1.5x——因为要交换的是 KV，不是整个 activation。
- **教什么**：prefill 和 decode 该用不同的并行方式；这也解释了为什么
  `docs/multigpu.md` 里 prefill 那一行反而更好看。

### S10 — 真身（3–4 天）

- **问题**：用老鼠学到的成本模型，能不能预测 27B 的数字？
- **建**：切仓库里的 checkpoint，2 卡跑起来（或者把 rat 引擎按 27B 的几何改）。
- **过关**：和 `T(n) = 8.35/n + 1.56 + 0.128·L` 差 10% 以内。
- **教什么**：模型能不能外推。差得远，说明固定成本那项你没看懂。

### S11 — 备忘（0.5 天）

- **产出**：两页纸——每种策略的适用条件、成本（tok/s/$、tok/s/W）、以及"如果
  L 变成 20 µs、或者 batch 变成 64，结论怎么变"。
- **教什么**：把十一级压成三句话，就是你能讲的东西。

## 4. 瓶颈 → 下一步（决策表）

跑完一级，先在这张表里找到响的那一条，再决定下一级做什么。这张表是整本手册
里最该背下来的一页。

| 现象（哪一条检查响了） | 下一个杠杆 | 典型收益 |
|---|---|---|
| eager 远慢于 graphed | 图捕获 | 3–10x |
| 消息翻倍、时间不翻倍 | 延迟受限：one-shot / 融合 / 减少次数 | 1.2–2x |
| step ≈ compute + comm，而不是 max | 拆 micro-batch、分块 all-reduce | 藏掉 30–50% 通信 |
| comm share > 20% | 把 all-reduce 融进 norm；每次多带 token | 5–15% |
| straggler > 5% | 重新分片；把采样挪到非关键卡 | 2–5% |
| 已经 ≥ 80% 聚合墙 | 别再切了，去量化 | — |
| S(2n) ≈ S(n) | 固定税见顶，停止加卡 | — |

## 5. 日志模板

每一级都按这个骨架记，**预测必须在跑之前写**——这是"学习"和"跑分"的唯一区别。

```markdown
## Sn — 名字（日期，机器）
**问题**：
**预测（跑之前写）**：具体数字 + 理由
**做了什么**：文件、关键参数
**测到**：
| 配置 | ms | tok/s | GB/s | %墙 | comm share | straggler |
**瓶颈**：哪一条检查响了 + 证明它的那个数
**对错**：预测偏了多少，为什么
**下一步**：这个结果强制了什么决定，门槛是多少
```

"对错"这一行最值钱。没有它，十一级跑完还是一本数字；有它，你才知道自己的
直觉错在哪。

## 7. 时间与钱

- **时间**：11 级约 45–70 小时；S7+ 再加 2 天。每周 15–20 小时，3–4 周。
- **机器**：2 × 5090 按 $2.5/hr 估，55 小时约 **$140**；2 × A100 SXM 三小时
  **$20–30**；4 卡那几小时 **$30–50**。全程 **$150–250**，比单卡那个项目
  贵不了多少，因为大部分问题一天内能答完。
- **下载**：27B 的 17 GB、draft 的 3.9 GB、老鼠 bf16 约 16 GB + int4 约 4.5 GB；

## 8. 结束时你应该能画出的图

一张 4×4 的表（TP / PP / DP / TP+PP × bs 1/8/64），每一格有 tok/s 和
comm share；跑过 S7+ 就再加一行 MoE。外加一句"如果 L 变成 20 µs / batch 变成
64，哪一格会翻"。

以及这句能脱口而出的话：

> 2×5090 上 27B@4.25bpw 单流 TP=2 是 1.5x，不是 2x：128 次 10 KB 的
> all-reduce 值 0.77 ms，而半步只有 4.2 ms；batch 到 64 时 PP 反超，因为
> 那时瓶颈从延迟变成了权重带宽。换成 MoE，bs=1 的账本整个反过来：只读激活的
> 3B，EP 反而是负收益。

能说出这句，多卡这块就算学明白了。
